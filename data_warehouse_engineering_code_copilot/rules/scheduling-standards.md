# 调度与运维规范

## 1. 调度系统约定

### 通用原则
- 一张表 = 一个调度作业（除非合并加工）
- 作业名 = 输出表名（避免 SQL 路径与作业名脱节）
- 严格基于上下游表完成度触发，不依赖固定时间

### 命名约定
```
{layer}_{biz_process}_{grain}_{period}
```
示例：
- `dwd_trade_order_di_daily`
- `dws_user_active_1d_daily`
- `ads_sales_dashboard_1d_daily`

实时作业加 `_rt` 后缀，小时级加 `_h`：
- `dwd_user_event_rt`
- `dws_user_active_1h_hourly`

---

## 2. 依赖关系

### 强依赖（Strong Dependency）
- 上游表当日分区就绪后才触发下游
- 通过 sensor / check 任务实现：等上游分区出现再启动
- 跨集群依赖必须配置 webhook / 跨集群 sensor

### 弱依赖（Weak Dependency）
- 仅在上游存在新数据时启动，否则跳过
- 适用于事件驱动型作业（CDC / 实时）

### 依赖配置示例
```yaml
# 调度配置（以 DolphinScheduler / Airflow 为例的概念结构）
job: dws_user_active_1d_daily
schedule: 0 2 * * *      # 每日凌晨 2 点
upstream_dependencies:
  - dwd_user_event_di_daily    # 当日分区就绪
  - dim_user_zip_daily         # 维度就绪
sla: 06:00                # 必须 6 点前完成
retry: 3                  # 重试 3 次
retry_interval: 5m        # 间隔 5 分钟
priority: HIGH
queue: dwh_core
alert:
  on_failure: [ops-team, owner]
  on_timeout: [owner]
  on_sla_miss: [data-team-lead]
```

## 3. 调度周期

| 周期 | 适用场景 | 触发时间建议 |
|------|---------|-------------|
| 实时（rt） | 用户行为流、风控 | 持续运行，checkpoint 30s ~ 60s |
| 小时级（hourly） | 高时效报表、监控 | 每小时 05 分 |
| 天级（daily） | 主流数仓作业 | 02:00 ~ 06:00（依赖链有序） |
| 周级（weekly） | 周报、慢更新维度 | 周一 06:00 |
| 月级（monthly） | 月报、归档 | 月初 1 日 06:00 |
| 按需 | 探索、回刷 | 手动触发 |

## 4. SLA 与基线

### 基线定义
- **核心基线**：决定全公司报表能否按时产出（如 7:00）
- **业务基线**：特定业务方要求（如 9:00 前财务日报）
- **观察基线**：监控但不告警（如 12:00）

### 基线设置原则
- 核心 ADS 必须有基线
- DWS 基线 = ADS 基线 - ADS 处理时长 - 缓冲
- DWD 基线 = DWS 基线 - DWS 处理时长 - 缓冲
- 缓冲建议：每层留 30 分钟

### 基线告警
- 基线前 1 小时：预警通知 owner
- 基线前 30 分钟未启动：告警 + 升级
- 错过基线：告警业务方 + 启动 RCA

## 5. 重试与告警

### 重试策略
| 失败类型 | 重试 | 间隔 |
|---------|------|------|
| 资源不足 / 超时 | 3 次 | 指数退避 1m → 5m → 15m |
| 上游延迟 | 等待上游 + 自动重试 | 30m 上限 |
| 数据问题（DQ 失败） | 不重试，直接告警 | - |
| 代码 bug | 不重试 | - |

### 告警等级
| 等级 | 触发条件 | 通知渠道 |
|------|---------|---------|
| P0 | 核心基线失败 / 数据错误 | 电话 + 短信 + IM |
| P1 | 重要作业失败 / SLA 失守 | 短信 + IM |
| P2 | 普通作业失败 | IM |
| P3 | DQ 告警（不阻断） | 邮件 / 日报 |

### 告警去重
- 同作业 5 分钟内仅告警 1 次
- 上游失败导致下游级联失败 → 只告警上游
- 重试中不告警，重试用尽才告警

## 6. 资源队列

### 队列划分
| 队列 | 用途 | 资源占比 |
|------|------|---------|
| `dwh_core` | 核心 ADS / 关键 DWS | 40% |
| `dwh_general` | 普通 DWD / DWS | 30% |
| `dwh_ops` | 回刷 / 数据修复 | 10% |
| `dwh_explore` | 探索 / 临时查询 | 10% |
| `dwh_realtime` | 实时作业 | 10% |

### 资源申请
- 默认资源 spec 由模板提供
- 大型作业（> 1TB / > 1 小时）需评审申请
- 紧急回刷使用 `dwh_ops` 队列

## 7. 调度脚本规范

### 脚本头
所有调度脚本必须包含：
```sql
-- ============================================
-- 作业名：xxx
-- 用途：xxx
-- 调度：daily / hourly / cron, ${schedule}
-- 上游：表 1, 表 2
-- 下游：表 a, 表 b
-- 责任人：xxx
-- ============================================
```

### 变量约定
统一使用调度系统标准变量名：
| 变量 | 含义 | 示例 |
|------|------|------|
| `${bizdate}` | 业务日期 YYYYMMDD | 20260603 |
| `${bizdate_minus_1}` | 业务日期 - 1 | 20260602 |
| `${bizdate_plus_1}` | 业务日期 + 1 | 20260604 |
| `${cyctime}` | 调度执行时间 | 20260604020000 |
| `${gmtdate}` | 业务日期，'-' 分隔 | 2026-06-03 |

### 幂等保证
- 所有写入必须 `INSERT OVERWRITE` 单分区
- 多分区批量写入必须先校验目标分区是否存在数据
- 禁止 `DROP TABLE` 出现在调度脚本

## 8. 上线流程

### 必须步骤
1. **代码评审**：SQL / DDL / 调度配置 PR review
2. **测试环境验证**：开发库跑 7 天数据，对比基准
3. **数据质量规则上线**：DQ 与作业同步上线
4. **生产首跑**：选定首跑日期，监控运行
5. **历史回刷**：确认首跑正确后再批量回刷
6. **观察期**：上线后 7 天人工 review 数据
7. **变更日志**：通过 version-tracker 记录

### 严禁
- ❌ 直接在生产库写 SQL（必须经过开发→测试→生产）
- ❌ 跳过测试环境
- ❌ 没有 DQ 规则的核心作业上线
- ❌ 没有上下游通知的破坏性变更（删表 / 改主键 / 改粒度）

---

## 9. 监控与可观测性

### 必备监控
- 作业成功率（按层 / 按主题）
- 作业运行时长（P50 / P95 / 异常）
- 数据产出延迟（vs 基线）
- 数据量趋势（行数环比 / 同比）
- DQ 通过率
- 资源消耗趋势

### 异常分析
- 单作业耗时 > P95 × 1.5 → 告警
- 行数环比下降 > 30% / 上升 > 200% → 告警
- 关键字段非空率下降 > 1pp → 告警

---

## 10. 失败回放与回退

### 回放
- 单分区失败：重试或人工补跑
- 多分区批量失败：确认根因后批量回刷
- 上游补数：等上游就绪后人工触发本作业

### 回退
- 代码 bug：rollback 到上一版本，回刷受影响分区
- 模型 bug：先停下游，修模型，从 DWD 开始回刷
- 数据错误：禁用下游报表，对外说明 ETA

### 回退脚本（伪代码）
```bash
# 1. 停所有依赖该表的下游
freeze_downstream dwh_dwd.dwd_trade_order_di

# 2. 回滚代码到指定版本
git checkout <prev_commit> sql/dwd/dwd_trade_order_di.sql

# 3. 回刷指定分区
for d in 20260601 20260602 20260603; do
    rerun_job dwd_trade_order_di_daily --date=$d
done

# 4. 验证后解冻下游
verify_then_unfreeze dwh_dwd.dwd_trade_order_di
```
