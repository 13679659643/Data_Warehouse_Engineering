# dwh-copilot 数仓开发 AI 协作助手 — 目录结构和设计说明

> 面向数据仓库（Data Warehouse）开发场景的 AI 数据分析与建模协作助手。
> 核心理念：**Spec 驱动 + 三段式知识库 + 强制变更追踪**。

---

## 1. 项目定位

`dwh-copilot` 是一套可加载到 AI 编码助手中的"工程化提示词工程"项目，让 AI 在数仓开发中：

- 像顶尖数仓工程师一样，遵循统一的 SQL / 建模 / 调度 / 安全 规范
- 强制走"需求 → spec → 任务 → 实施 → 审查 → 归档"的完整闭环
- 复用沉淀的 SQL 模式、ETL 模式、建模技巧、性能优化经验
- 自动追踪每次 DDL / SQL / ETL / 调度变更，形成可审计的变更日志

## 3. 核心设计原则

### 3.1 Spec 驱动（Model is Cheap, Context is Expensive）
SQL 脚本、调度作业、模型 DDL 都是可重建的消耗品；**需求文档（Spec）才是昂贵的核心资产**。

四条铁律：
1. **No Spec, No Change** — 没有 spec，不准改表 / 调度 / 核心 SQL
2. **Spec is Truth** — spec 与实现冲突时，错的一定是实现
3. **Reverse Sync** — 发现偏差先改 spec 再改实现
4. **变更即记录** — 任何变更必须更新 changes/ 与 changelog

### 3.2 三段式知识结构

| 目录 | 角色 | 关系 |
|------|------|------|
| `rules/` | **约束** — 必须遵守的"红线" | 强制 |
| `knowledge/` | **经验** — 可复用的"工具箱" | 推荐 |
| `changes/` | **过程** — 每次变更的"病历" | 历史 |

知识飞轮：**实践 → changes/log.md 知识发现 → /archive 沉淀 → knowledge/ 复用**。

### 3.3 命令式协作

通过 `/sql /etl /model /propose /apply /review /optimize /dq /schedule /archive` 等命令，让 AI 在固定流程内工作，避免发散与遗漏：

| 命令 | 触发场景 |
|------|---------|
| `/init` | 新项目初始化数仓上下文 |
| `/sql` | 单段 SQL 加工开发 |
| `/etl` | 数据接入 / 同步任务开发 |
| `/model` | 数仓建模（事实/维度/分层） |
| `/propose` | 创建变更提案（生成 spec） |
| `/apply` | 按 spec / tasks 实施 |
| `/review` | 三阶段审查（合规 → 模型 → SQL） |
| `/optimize` | 性能诊断与优化 |
| `/dq` | 数据质量校验与对账 |
| `/schedule` | 调度配置与依赖 |
| `/archive` | 归档 + 知识沉淀 |

### 3.4 强制变更追踪

`agents/version-tracker.md` 在每次 DDL / SQL / ETL / 调度变更后**自动**追加结构化日志，包含：
- 时间（精确到分）、模块、分层、操作类型
- 精确到 库.表.字段 / 作业名 的变更内容
- 关联文件、回刷范围、下游影响

确保**所有变更都可审计、可回溯**。

## 4. 数仓特色设计

相比通用数据分析助手，本项目针对数仓场景做了以下强化：

| 维度 | 数仓特色设计 |
|------|------------|
| **建模** | 严格分层（ODS/DWD/DWS/ADS/DIM），强制命名规范，覆盖 SCD 全套策略 |
| **SQL** | 强制分区裁剪、幂等覆盖、CTE 命名、头部注释 |
| **ETL** | 全量/增量/CDC 三选一选型对照表，幂等与回放优先 |
| **调度** | 上游就绪触发、SLA 基线倒推、错峰调度、失败回放 |
| **数据质量** | 五维度规则模板（完整/唯一/一致/准确/时效）+ 上线流程 |
| **审查** | 三阶段串行（Spec 合规 → 模型质量 → SQL 质量），不通过不进下一阶段 |
| **回刷** | 分批回刷 + 进度跟踪 + 影响下游通知 |
| **安全** | 字段脱敏、行级权限、数据分级、跨境合规 |

## 5. 典型工作流

### 场景 A：新建一个数据需求

```
用户："给销售域加一张 ADS 月度销售看板表，按门店 × 商品类目维度"
  ↓
dwh-copilot 识别为 /propose
  ↓
1) Research：扫描 rules/project-context.md 找已有 dws_sales_*、dim_shop、dim_sku
2) 逐个澄清：粒度？时间窗？是否含退款？SLA？
3) 生成 changes/<change-name>/spec.md
   含：模型变更 DDL、SQL 设计、调度配置、DQ 规则
4) 生成 changes/<change-name>/tasks.md（按 ODS→DIM→DWD→DWS→ADS 顺序）
5) HARD-GATE：等待用户确认
  ↓
用户："开始实施"
  ↓
dwh-copilot 走 /apply
  ↓
逐 task 执行，每个 task 完成后：
- 展示验证证据（行数/抽样/对账三选一）
- 触发 version-tracker 写入 changelog
  ↓
全部完成后：/review（三阶段审查）→ /archive（归档 + 知识沉淀）
```

### 场景 B：性能优化

```
用户："dws_user_active_1d 跑了 2 小时，太慢"
  ↓
dwh-copilot 走 /optimize
  ↓
按 数据源→ETL→数仓→SQL→应用 五层诊断
找到根因（如：未分区裁剪 + 倾斜键 + 小文件）
  ↓
给出具体修改 + 优化前后量化对比
  ↓
触发 version-tracker → 沉淀到 knowledge/performance-tips.md
```

## 6. 与 powerbi_code_copilot 的差异

本项目结构参考自 [powerbi_code_copilot](../Qoder_AI_Frontend_and_backend_Web/powerbi_code_copilot/)，但针对数仓场景做了系统性替换：

| powerbi_code_copilot | dwh_code_copilot |
|---------------------|------------------|
| DAX / Power Query | SQL（Hive/Spark/MaxCompute）/ ETL |
| 模型（表关系） | 数仓分层 + 维度建模 |
| 度量值 | 指标 / KPI 字典 |
| 报表/可视化 | ADS 表 + 调度 + DQ |
| 切片器知识库 | 维度建模技巧（SCD/桥接/退化） |
| 可视化规范 | 调度规范 + 数据质量规范 |
| RLS | RLS + 字段脱敏 + 数据分级 |

## 7. 使用方式

1. 将本项目目录加载到 AI 编码助手的工作区 / 系统提示词
2. 让 AI 阅读 `agents/copilot-prompt.md` 作为主提示词
3. 在每次会话开始时，AI 会自动扫描 `rules/`、`changes/` 当前进行中的变更
4. 通过命令（`/sql`、`/propose`、`/apply` 等）开展协作
5. 首次使用某项目时执行 `/init` 让 AI 填充 `rules/project-context.md`
